# 權限控管基準線

本基準線定義 StockFlow 進入正式營運前的登入、角色與權限邊界。權限控管不是只為了「看不看得到按鈕」，而是要保護庫存、金流、成本、毛利、作廢、備份還原與審核責任。

## 核心原則

- 權限以角色為基礎，未來可再加到個人帳號。
- 高風險操作必須可追溯操作者、時間與原因。
- 使用者沒有權限時，操作入口應保持可見但 disabled，並說明原因。
- 權限限制要同時存在於 UI 與資料寫入層，不能只靠隱藏按鈕。
- 單機版第一階段可使用「本機管理者」模式，但資料模型要保留 `createdBy`、`approvedBy`、`voidedBy` 等欄位。

## 角色

| 角色 | 定位 |
|---|---|
| `owner` 老闆 / 管理者 | 全部權限，包含設定、備份還原、作廢、財務、權限配置。 |
| `purchasing` 採購 | 建立採購與供應商資料，可看商品與庫存，不預設看銷售毛利。 |
| `sales` 銷售 | 建立銷售與客戶資料，可看可售庫存，不預設看成本、應付與毛利。 |
| `warehouse` 倉管 | 看庫存、調撥、盤點、待驗區，不預設看財務。 |
| `finance` 財務 | 看應收、應付、收付款與財務報表，不預設改庫存。 |
| `auditor` 稽核 / 查詢 | 只能查詢紀錄、作廢原因、反向事件與報表，不可改資料。 |

第一階段若尚未登入，預設角色為 `owner`，但 UI 應清楚標示「本機管理者」。一旦導入多人或雲端同步，未登入者不得寫入資料。

### 操作權限細分

第一版操作權限需避免用同一個 `submitDocument` 或 `confirmDocument` 套到所有單據，至少拆到採購、銷售與倉管確認：

| 操作 | owner | purchasing | sales | warehouse | finance | auditor |
|---|---:|---:|---:|---:|---:|---:|
| 採購單送審 | 是 | 是 | 否 | 否 | 否 | 否 |
| 銷售單送審 | 是 | 否 | 是 | 否 | 否 | 否 |
| 核准單據 | 是 | 否 | 否 | 否 | 否 | 否 |
| 退回單據 | 是 | 否 | 否 | 否 | 否 | 否 |
| 確認採購入庫 | 是 | 否 | 否 | 是 | 否 | 否 |
| 確認銷售出庫 | 是 | 否 | 否 | 是 | 否 | 否 |
| 建立進貨退貨 | 是 | 是 | 否 | 是 | 否 | 否 |
| 建立銷售退貨 | 是 | 否 | 是 | 是 | 否 | 否 |
| 登錄收付款 | 是 | 否 | 否 | 否 | 是 | 否 |

守門原則：

- 採購負責提出 PO，不直接確認庫存入庫。
- 銷售負責提出 SO，不直接確認庫存出庫。
- 倉管負責確認實際入庫、出庫、盤點與調撥，但不看敏感金額。
- 財務負責收付款與沖帳，不直接改庫存單據。
- 稽核可看紀錄與關聯，不可寫入。

## 高風險權限

下列操作必須視為高風險：

- 備份還原。
- 作廢已確認單據。
- 建立反向事件或沖銷單據。
- 修改商品成本。
- 修改已確認單據。
- 刪除草稿。
- 調整庫存與調撥。
- 收款、付款與沖帳。
- 查看毛利、成本與應付。

高風險操作至少需記錄：

| 欄位 | 說明 |
|---|---|
| `requestedBy` | 操作申請人。 |
| `approvedBy` | 核准人，若不需審核可與操作者相同。 |
| `operatedBy` | 實際執行人。 |
| `operatedAt` | 執行時間。 |
| `reason` | 操作原因。 |
| `roleAtOperation` | 操作當下角色。 |

## 第一階段實作邊界

第一階段可以先不做真正帳號登入，但需先預留：

- `currentUser` 狀態。
- `role` 欄位。
- 單據上的 `createdBy`、`confirmedBy`、`approvedBy`、`voidedBy`。
- 操作前的 `canPerform(action, context)` 判斷。
- disabled reason 文字。

單機版若以本機管理者執行，作廢欄位可先寫入 `本機使用者`，但日後導入登入時必須改為實際帳號。

## 與其他基準線的關係

- 審核流程需引用本基準線決定誰可送審、核准、退回與確認。
- 作廢與反向事件需引用本基準線決定誰可申請與核准。
- 備份還原需引用本基準線，預設只有 `owner` 可執行。
- 雲端同步導入後，權限不能只存在 localStorage，必須由服務端再次驗證。

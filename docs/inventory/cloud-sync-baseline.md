# 多人同步與雲端資料庫基準線

本基準線定義 StockFlow 從本機 localStorage 走向多人同步與雲端資料庫前必須先決定的架構邊界。多人同步不是單純把資料放到雲端，而是要處理權限、衝突、離線、資料鎖定、審核與稽核。

## 核心原則

- localStorage 適合單機，不適合多人正式營運。
- 多人同步導入後，服務端是主要事實來源。
- 寫入資料需由服務端再次驗證權限與資料狀態。
- 單據編號不可由多台瀏覽器各自猜測。
- 衝突不可靜默覆蓋，需提示並保留可追溯紀錄。

## 架構階段

| 階段 | 說明 |
|---|---|
| 單機版 | localStorage 儲存，適合單人或單機使用。 |
| 備份交換版 | 透過 JSON 匯出匯入交換資料，需人工控管版本。 |
| 雲端同步版 | 服務端資料庫、登入、權限、同步與衝突處理。 |
| 離線優先版 | 可離線建立草稿，恢復連線後送審或同步。 |

## 雲端資料模型要求

雲端資料需至少支援：

- `tenantId`：公司或帳套。
- `userId`：操作者。
- `role`：角色。
- `documentNo`：服務端產生或保證唯一。
- `version`：資料版本。
- `updatedAt`：最後更新時間。
- `updatedBy`：最後更新者。
- `deletedAt`：只允許草稿刪除時使用。
- `auditLog`：高風險操作紀錄。

## 同步策略

- 讀取時取得最新版本與本機快取。
- 寫入時帶上目前版本。
- 服務端若發現版本落後，拒絕寫入並回傳衝突。
- 使用者需選擇重新載入、另存草稿或人工合併。
- 已確認單據不得被舊資料覆蓋。

## 衝突處理

| 衝突 | 處理 |
|---|---|
| 同一商品被兩人修改 | 顯示差異，需人工選擇。 |
| 同一單據被修改與確認 | 以已確認版本為準，修改者需重新送審。 |
| 同時作廢同一單據 | 第一筆成功，第二筆提示已作廢。 |
| 同時建立單據 | 由服務端發號，避免重複單號。 |
| 離線建立草稿 | 重新連線後送審或重新取號。 |

## 鎖定與審核

- 已送審單據可鎖定明細。
- 已確認單據不可直接修改。
- 備份還原在雲端版需停用或改成管理員匯入流程。
- 會計期間鎖帳後，不可修改該期間有效交易，只能反向事件。

## 安全與權限

- 權限必須在服務端驗證。
- 備份匯出需權限控管。
- 財務、成本、毛利資料需分權限。
- 操作紀錄不可由前端自行刪除。
